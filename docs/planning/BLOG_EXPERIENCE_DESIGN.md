# GitHub Pages 블로그 제품·UX·UI 디자인 기획

> 상태: 블로그 경험 MVP는 P3·P5에서 구현됨. 2.3절과 6.4절, 10절은 재작성 Q1에서 승인된 A 작업대형 기준(2026-11-10)이다.
>
> 대상: `packages/publisher`가 생성하는 Astro 기반 GitHub Pages 블로그, 게시 전 프리뷰, 게시 앱 칸반 화면
>
> 기준 문서: `docs/spec/PROJECT_SPEC.md`, `TECH_RULES.md`, `docs/architecture/ARCHITECTURE.md`
>
> 작성일: 2026-08-09

## 1. 문서 목적

Notion Kanban Blog의 게시 결과를 단순한 글 목록에서 **읽기 쉽고, 탐색 가능하며, 게시 전에 결과를 확신할 수 있는 개인 블로그**로 발전시키기 위한 제품·UX·UI 기준을 정의한다.

이 문서는 구현 명세가 아니라 다음 구현의 기준이 되는 경험 설계다. 앱의 DB 없는 구조, 사용자별 공개 `<login>.github.io` 저장소, 서버가 최신 Notion 원문과 권한을 다시 검증하는 게시 경계, Astro 정적 빌드라는 기존 원칙을 유지한다.

### 성공 기준

- 작성자는 게시 전에 홈·글 상세의 실제 레이아웃과 콘텐츠 변환 결과를 확인할 수 있다.
- 독자는 홈에서 최신 글과 주제를 이해하고 2번 이내의 이동으로 원하는 글을 연다.
- 카테고리와 태그의 역할이 겹치지 않고, 메타데이터가 없어도 게시가 막히지 않는다.
- 모바일 320px부터 데스크톱까지 핵심 읽기·탐색 기능이 손실되지 않는다.
- 키보드, 스크린 리더, 확대, 모션 감소 환경에서 동등한 정보를 제공한다.
- 빈 상태와 외부 이미지·빌드·경로 오류가 레이아웃 붕괴나 막다른 화면으로 이어지지 않는다.

### 비목표

- 테마 마켓, 사용자 CSS 편집기, WYSIWYG 편집기
- 댓글, 구독, 검색 서버, 분석 대시보드
- 팀 블로그, 다중 작성자 권한, 비공개 글, 예약 게시
- 서버 DB를 이용한 프리뷰·분류·게시 이력 저장

## 2. 현행 기준선과 설계 제약

### 2.1 현행 `packages/publisher` 템플릿

현재 template version 1은 다음 정적 파일을 만든다.

- `src/pages/index.astro`: `publishedAt` 역순의 전체 글 목록과 빈 상태
- `src/pages/posts/[...slug].astro`: 제목, 게시일, 변환된 본문
- `src/layouts/BaseLayout.astro`: `Notion Blog` 헤더와 최대 48rem 단일 컬럼
- `src/content.config.ts`: `title`, `description`, `publishedAt`, `updatedAt` 스키마
- 전역 색상: 본문 `#211f1b`, 배경 `#f7f4ee`, 경계 `#d9d2c6`, 보조 글자 `#716b62`

지원 본문은 문단, h2–h4, 인용, 코드, HTTPS 이미지, 토글, 구분선과 안전한 rich text다. user site와 project site의 base path가 모두 지원되지만 제품 MVP의 실제 게시 대상은 사용자 소유 공개 `<login>.github.io`다.

### 2.2 현행과 목표 사이의 차이

| 영역 | 현행 | 목표 | 계약 영향 |
|---|---|---|---|
| 홈 | 전체 글 단순 목록 | 소개, 최신 글, 주제 탐색, 명확한 빈 상태 | 템플릿 변경 |
| 글 상세 | 제목·게시일·본문 | breadcrumb, 설명, 분류, 수정일, 본문 목차, 이전/다음 글 | 템플릿 변경 |
| 분류 | 없음 | 카테고리 0–1개, 태그 0–5개 | 콘텐츠 스키마·정규화 변경 |
| 경로 | `/`, `/posts/:slug/` | `/categories/:slug/`, `/tags/:slug/` 추가 | 정적 route 추가 |
| 프리뷰 | 없음 | 게시 전 최신 Notion 기준의 읽기 전용 프리뷰 | 앱/API 계약 추가 |
| 브랜드 | 고정 `Notion Blog` | 최소 사이트 제목·소개 설정 | 설정 저장 계약 별도 필요 |

카테고리, 태그, 프리뷰는 현행 publisher 입력 계약에 없다. 따라서 아래의 “경험 MVP”는 기존 제품 MVP 위에 얹는 다음 제품 범위이며, 구현할 때 `PROJECT_SPEC`와 publisher 계약을 먼저 갱신해야 한다. 이 문서만으로 브라우저가 Markdown이나 provider 결과를 게시 요청에 대신 전달하도록 해서는 안 된다.

### 2.3 재작성 시각 방향: A 작업대형 (2026-11-10 승인)

재작성 Q1에서 세 방향(A 작업대형, B 편집국형, C 집중형) 시안을 비교했고 사용자가 앱과 블로그 모두 A를 골랐다. A는 작업 도구처럼 차분하게 보이는 것을 목표로 한다.

- 게시 앱: 왼쪽에 Notion 문서 트리를 고정하고 나머지 폭 전체를 3열 칸반으로 쓴다. 게시 대상 repository 상태는 상단 바의 상태 표시 하나로 줄인다(6.4절).
- 블로그: 장식 없는 개발 블로그. 글은 한 열로 읽고, desktop에서는 목차를 옆에 붙인다. 날짜·분류 같은 메타 정보는 mono 글꼴로 본문과 구분한다.
- 시각 언어: 흰 surface와 옅은 회색 바탕, 강조색은 파랑 하나만 쓴다. serif 제목, 종이색 배경, 그림자 강조는 쓰지 않는다. 토큰은 10절에 둔다.
- 현행에서 고칠 문제: 칸반이 탐색 패널 안에 들어가 있음, 미리보기 버튼 중복, 게시 대상 정보가 페이지 끝에 떨어져 있음, 320px에서 제목과 버튼이 잘림.

## 3. 사용자와 핵심 요구

### 작성자

- Notion의 문서 구조가 블로그에서 어떻게 보일지 게시 전에 확인하고 싶다.
- 별도 CMS를 배우지 않고도 글을 주제별로 정리하고 싶다.
- 게시 실패가 콘텐츠, 권한, GitHub Actions 중 어디에서 생겼는지 알고 싶다.
- 다시 게시할 때 새 commit이 생기며 프리뷰는 게시 상태를 저장하지 않는다는 점을 이해해야 한다.

### 독자

- 블로그의 주제와 최근 글을 첫 화면에서 파악하고 싶다.
- 같은 카테고리의 글과 관련 태그 글을 이어 읽고 싶다.
- 작은 화면에서도 긴 글, 코드, 이미지, 토글을 편안하게 읽고 싶다.
- 없는 글이나 비어 있는 분류에서도 다음 이동 경로를 찾고 싶다.

## 4. 경험 원칙

1. **글이 가장 먼저다.** 장식보다 제목, 설명, 본문 리듬과 탐색을 우선한다.
2. **프리뷰와 실제 결과의 간극을 줄인다.** 동일한 렌더링 컴포넌트·토큰·base path 규칙을 사용한다.
3. **분류는 선택 사항이다.** 메타데이터가 없어도 `전체 글`에서 정상 게시·탐색된다.
4. **상태는 말로 설명한다.** 색이나 아이콘만으로 카테고리, 선택, 오류, 외부 링크를 표현하지 않는다.
5. **정적 사이트의 장점을 지킨다.** 핵심 탐색과 본문은 JavaScript 없이 동작한다.
6. **안전한 원문이 기준이다.** 프리뷰와 게시 모두 서버가 최신 Notion 권한·원문을 다시 조회하고 정규화한다.

## 5. 정보 구조

### 5.1 사이트 맵

```text
블로그
├─ 홈 /
│  ├─ 사이트 소개
│  ├─ 최신 글
│  └─ 카테고리 탐색
├─ 전체 글 /posts/
├─ 카테고리 /categories/:categorySlug/
│  └─ 해당 카테고리 글 목록
├─ 태그 /tags/:tagSlug/
│  └─ 해당 태그 글 목록
├─ 글 상세 /posts/:postSlug/
└─ 찾을 수 없음 /404.html

게시 앱
└─ 프리뷰 /preview/:connectionId/:providerPageId  (외부 공개 경로 아님)
   ├─ 홈 탭
   └─ 글 상세 탭
```

경험 MVP의 전역 내비게이션은 `사이트명`, `홈`, `전체 글`, `카테고리`를 둔다. 홈에는 최신 글 12개만 두고 `/posts/`에서 모든 글을 탐색하게 해 오래된 미분류 글도 막힘없이 찾을 수 있게 한다. 태그는 전역 메뉴가 아니라 글 상세와 카드에서 맥락적으로 진입한다.

### 5.2 카테고리와 태그 모델

| 구분 | 카테고리 | 태그 |
|---|---|---|
| 목적 | 블로그의 큰 주제와 1차 탐색 | 글의 세부 개념과 횡단 탐색 |
| 글당 수 | 원문 0 또는 1, 게시 결과는 fallback을 포함해 1 | 0–5 |
| 전역 노출 | 홈과 내비게이션 | 글 카드·글 상세 |
| 정렬 | 글 수 내림차순, 이름 오름차순 | 글 안에서는 지정 순서, 목록은 이름순 |
| 미지정 | `미분류`/`uncategorized`로 모아 기존 글도 탐색 가능하게 함 | 태그 영역을 렌더링하지 않음 |
| 표시명 | 원문 대소문자·한글 보존 | 원문 보존, 앞에 `#` 표시 |
| 식별 | 정규화 slug | 정규화 slug |

분류 slug는 표시명과 분리한다. Unicode 표시명은 보존하되 route slug는 publisher의 안전한 slug 규칙을 따른다. 충돌 시 안정적인 짧은 hash suffix를 붙인다. 대소문자, 앞뒤 공백, Unicode 정규화만 다른 값은 같은 분류로 합친다.

메타데이터의 제품 기준 원천은 Notion page/database의 명시적 속성이다. 예약 속성명은 `Blog Category`(select)와 `Blog Tags`(multi-select)이며, 속성이 없으면 각각 `미분류`와 빈 목록으로 처리한다. 속성이 존재하지만 형식이 잘못되면 조용히 보정하지 않고 프리뷰·게시에서 명시적으로 안내한다. 브라우저가 임의의 분류 값을 게시 payload로 전달하는 방식은 사용하지 않는다. 서버 orchestration이 현재 권한으로 다시 읽어 내부 문서 모델로 정규화해야 한다.

### 5.3 URL과 링크 규칙

- 내부 링크는 Astro `base`를 항상 반영해 user/project site 모두 안전해야 한다.
- 모든 목록·분류 URL은 trailing slash를 사용한다.
- 사이트명은 항상 홈으로 이동한다.
- breadcrumb는 `홈 / 카테고리 / 글`의 계층을 표현하되 카테고리가 없으면 `홈 / 글`로 축약한다.
- 외부 링크는 새 탭을 강제하지 않는다. 새 탭을 쓰는 게시 앱의 “실제 블로그 열기”에는 새 창임을 접근 가능한 이름으로 알린다.

## 6. 게시 앱 화면

### 6.1 진입과 목적

보관 중 카드의 제목 또는 `미리보기` 보조 액션으로 연다. 기존의 “게시 중 column에 drop하면 즉시 게시” 규칙과 별도 게시 버튼 없음은 유지한다. 프리뷰는 게시를 실행하는 확인 단계가 아니라 선택 가능한 품질 점검 도구다.

프리뷰는 다음을 보장한다.

- 서버가 프리뷰 요청마다 세션, 연결 소유권, Notion page 접근을 확인한다.
- 최신 Notion page와 block을 publisher의 동일한 내부 문서 모델로 변환한다.
- credential, 원시 provider 응답, 전체 Markdown을 URL·로그·IndexedDB에 남기지 않는다.
- 프리뷰 결과와 선택 탭은 화면 메모리에만 둔다.
- 실제 게시 시에도 원문을 다시 조회하므로 프리뷰 이후 변경되면 결과가 달라질 수 있음을 표시한다.

### 6.2 레이아웃과 동작

- 상단 앱 바: `프리뷰`, 문서 제목, `Notion에서 마지막 수정 …`, 닫기
- 상태 안내: “이 화면은 저장되지 않습니다. 게시 시 최신 Notion 내용으로 다시 생성합니다.”
- 뷰 전환: `글 상세`(기본), `홈에서 보기`
- viewport 전환: `모바일 390`, `태블릿 768`, `데스크톱 1280`; 실제 콘텐츠 프레임 폭만 바꾸며 브라우저 UA를 흉내 내지 않는다.
- 렌더 영역: 실제 블로그의 header, token, component를 재사용한 격리된 preview surface
- 경고 패널: 지원하지 않는 block, 누락된 설명/분류, 불러오지 못한 외부 이미지. 경고는 프리뷰를 막지 않으며 치명 오류만 렌더를 중단한다.
- 하단 안내: “게시하려면 프리뷰를 닫고 카드를 게시 중으로 옮기세요.”

프리뷰 로딩 중에는 프레임 크기를 유지하는 skeleton과 `최신 Notion 내용을 불러오는 중` 상태를 함께 표시한다. 10초 이상이면 “평소보다 오래 걸리고 있습니다”를 추가하고 취소를 제공한다.

### 6.3 프리뷰 상태

| 상태 | 화면 | 행동 |
|---|---|---|
| 로딩 | 고정 프레임 skeleton + 텍스트 status | 닫기/취소 |
| 성공 | 실제 렌더 + 수정 시각 | 탭·viewport 전환 |
| 경고 | 렌더 유지 + 상단 경고 요약 | 경고 위치로 이동 |
| 권한 만료 | 프레임 대신 연결 오류 | Notion 다시 연결, 닫기 |
| rate limit | 재시도 가능 시간 안내 | 다시 시도 |
| 변환 실패 | 안전한 오류 요약과 block 종류 | Notion에서 수정, 다시 시도 |
| 오프라인 | 캐시된 본문을 보여주지 않음 | 연결 복구 후 다시 시도 |

### 6.4 칸반 앱 화면 (A 작업대형)

화면은 위에서부터 상단 바, 문서 사이드바, 칸반 순서로 구성한다. DOM 순서도 이와 같다.

| 영역 | 내용 | 규칙 |
|---|---|---|
| 상단 바 | 앱 이름, 게시 대상 상태(`<login>.github.io · 게시 준비 완료` 등), 계정 메뉴(Notion 연결·로그아웃) | 게시 대상 상태는 점과 문구를 함께 써서 색에만 의존하지 않는다. 준비가 안 된 상태에서 누르면 복구 안내(Pages 설정 링크, Actions 로그)를 펼친다. |
| 문서 사이드바 (`nav`) | 워크스페이스 선택과 `+ 연결`, 제목 검색, Notion 계층 트리 | 문서 행에는 상태 하나만 표시한다: `칸반`(이미 있음), `추가`(버튼), `폴더`(컨테이너, 펼치기만 가능), `구조 확인 중…`, `구조 다시 확인`(판별 실패). 미리보기는 사이드바에 두지 않는다. |
| 칸반 (`main`) | h1 `게시 칸반`, 한 줄 사용법, 열별 개수 요약, 3열(보관 중·게시 중·게시 완료) | 카드 하나에 행동은 `미리보기`, `칸반에서 빼기(✕)`만 둔다. 게시 중 카드는 진행 문구와 진행 막대, 완료 카드는 `게시된 글 보기` 링크를 보여준다. 게시 중 열에는 항상 `여기에 놓으면 게시` drop 영역을 둔다. |

상태별 화면:

| 상태 | 화면 |
|---|---|
| 로그인 전 | 상단 바와 한 화면짜리 소개, `GitHub로 시작` 하나. 칸반 모양 장식은 쓰지 않는다. |
| Notion 미연결 | 사이드바 자리에 `Notion 워크스페이스 연결` 안내와 버튼 하나. 칸반은 빈 열 3개를 보여준다. |
| 트리 로딩 | 사이드바 행 skeleton과 `role=status` 문구 |
| 빈 칸반 | 보관 중 열에 `왼쪽 문서 목록에서 추가하세요` |
| provider 오류·429 | 해당 영역 안에서 원인, 게시 여부, 다시 시도 버튼(대기 시간 동안 비활성)을 보여준다. 전체 화면을 막지 않는다. |
| 게시 실패 | 카드를 보관 중으로 되돌리고 카드 안에 실패 원인과 Actions 로그 링크를 둔다. |

반응형:

- 900px 이상: 사이드바 260–300px 고정 폭, 칸반 3열.
- 600–899px: 사이드바가 칸반 위로 올라가고 기본으로 접힌다(`문서 목록` 토글). 칸반은 2열부터 자동으로 줄바꿈한다.
- 320–599px: 칸반 열이 세로로 쌓인다. 카드 제목은 말줄임 없이 줄바꿈하고 버튼은 44px 이상 높이를 유지한다. 가로 스크롤이 생기지 않는다.
- keyboard drag(Space로 들고 방향키, Space로 놓기, Escape 취소)와 현재 위치 안내 `role=status`는 모든 폭에서 유지한다.

## 7. 공개 블로그 화면 설계

### 7.1 공통 셸

- Skip link: `본문으로 건너뛰기`
- header: 사이트명(owner login, 홈 링크), `전체 글`, `주제`, `GitHub`; 현재 위치는 `aria-current="page"`
- main: 화면별 단일 `h1`
- footer: 저작권 문구와 `GitHub Pages로 게시됨`; MVP에는 소셜 링크 없음
- 콘텐츠 최대 폭: shell 1120px, 본문 720px
- 모바일 내비게이션은 항목이 적으므로 햄버거 없이 가로 배치하고 줄바꿈을 허용한다.

### 7.2 홈

정보 우선순위는 소개 → 최신 글 → 카테고리다.

1. Hero: 사이트명, 1–2줄 소개. 과도한 이미지나 CTA는 두지 않는다.
2. 최신 글: 최대 12개. 첫 글도 같은 카드 규칙을 써 시각적 편향을 줄인다.
3. 카테고리: 이름과 글 수. 카테고리가 없으면 섹션 전체를 숨긴다.
4. 글 수와 관계없이 `전체 글 보기`를 제공한다.

글 카드는 카테고리, 제목, 설명 최대 2줄, 게시일, 태그 최대 3개를 표시한다. 카드 전체를 중첩 링크로 만들지 않고 제목 링크를 주 행동으로 둔다. hover 효과는 키보드 focus에서도 동일하게 제공한다.

### 7.3 카테고리

- breadcrumb: `홈 / 카테고리`
- h1: 카테고리 이름
- 보조 정보: `글 n개`
- 글 목록은 홈과 같은 카드로 일관성을 유지한다.
- 카테고리 이름이 URL에는 있지만 글이 없으면 404 대신 빈 카테고리 상태를 보여준다. 빌드 시 route가 생성되지 않는 정적 구현이라면 404가 이 역할을 대체하되 홈 이동을 제공한다.
- 카테고리 전환은 상단의 링크 목록으로 제공하며 2줄을 넘으면 가로 스크롤 대신 줄바꿈한다.

### 7.4 태그

태그 화면은 카테고리 목록 화면과 동일한 뼈대를 재사용하되 `#태그명`을 h1으로 쓴다. 태그는 전역 주 메뉴에 넣지 않는다. 글 카드에서는 태그 3개까지만 보이고 나머지는 `+n` 텍스트로 표시하며, 글 상세에서는 모두 제공한다.

### 7.5 글 상세

1. breadcrumb
2. 카테고리 링크(있을 때)
3. h1 제목
4. 설명
5. 게시일과 수정일: 날짜가 다를 때만 수정일 노출
6. 태그 목록
7. 선택적 목차: h2가 3개 이상일 때 생성, 데스크톱도 본문 위에 배치
8. 본문
9. 같은 카테고리 기준 이전/다음 글; 카테고리 없으면 전체 글 기준
10. `홈으로` 링크

본문 규칙:

- h1은 template만 생성하고 Notion heading은 h2–h4로 유지한다.
- 긴 URL과 일반 텍스트는 `overflow-wrap:anywhere`; 코드 블록은 가로 스크롤한다.
- 이미지는 원본 비율을 보존하고 caption이 있으면 `figcaption`으로 연결한다.
- 이미지 로딩 실패 시 alt/caption과 “이미지를 불러오지 못했습니다” 대체 상태를 유지한다.
- `details/summary`는 키보드 기본 동작을 보존하며 펼침 여부를 아이콘만으로 표현하지 않는다.
- 본문 링크는 밑줄을 기본 제공해 색에 의존하지 않는다.

## 8. 반응형 설계

CSS는 mobile-first로 구현하고 콘텐츠에 따라 자연스럽게 흐르게 한다.

| 구간 | 기준 | 레이아웃 |
|---|---:|---|
| Compact | 320–599px | 좌우 20px, 1열 카드, header 줄바꿈, 본문 18px |
| Medium | 600–899px | 좌우 32px, 글 목록 1열, 메타 정보 가로 정렬 |
| Wide | 900px 이상 | shell 최대 1120px, 홈 카드 2열 가능, 본문 720px 유지 |

- 200% 확대와 320 CSS px에서 양방향 페이지 스크롤이 생기지 않아야 한다. 예외는 코드 블록과 넓은 표 같은 내부 컨테이너다.
- 카드 grid는 `minmax(min(100%, 28rem), 1fr)` 방식으로 콘텐츠가 잘리지 않게 한다.
- 터치 target은 최소 44×44 CSS px, 인접 target 간 8px 이상 간격을 둔다.
- 모바일 프리뷰는 전체 화면 dialog, 데스크톱은 최대 1440px의 modal 또는 전용 화면을 쓴다.
- viewport 선택 UI는 실제 작은 화면에서는 숨기고 현재 폭 그대로 표시한다.

## 9. 접근성 기준

목표는 WCAG 2.2 AA다.

- 텍스트 대비 4.5:1 이상, 큰 텍스트·비텍스트 UI 3:1 이상
- DOM 순서와 시각 순서를 동일하게 유지
- 모든 화면에 하나의 h1과 순차적인 heading 구조
- skip link, landmark `header/nav/main/footer`, 설명적인 page title 제공
- focus indicator는 2px 이상이며 요소와 2px offset, 인접 색 대비 3:1 이상
- 프리뷰 modal은 열릴 때 제목으로 focus 이동, focus trap, Escape 닫기, 닫은 뒤 진입 요소로 focus 복귀
- loading은 `role=status`로 핵심 변화만 알리고 skeleton 자체는 `aria-hidden`
- 오류 요약은 `role=alert`를 남용하지 않고 새로 발생한 치명 오류에만 사용
- 날짜는 화면에는 지역화하되 `<time datetime>`으로 기계 판독값 제공
- 아이콘 버튼에는 보이는 텍스트 또는 접근 가능한 이름 제공
- `prefers-reduced-motion: reduce`에서 위치 이동·skeleton shimmer를 제거
- `prefers-contrast: more`에서 경계와 focus 대비를 강화
- 색상, `#`, 점 모양만으로 카테고리·태그·상태를 구분하지 않음
- 자동 재생, 시간 제한 상호작용, hover 전용 정보 없음

## 12. 빈 상태와 오류 상태

### 공개 블로그

| 상황 | 제목 | 설명 | 행동 |
|---|---|---|---|
| 첫 게시 전 홈 | 아직 게시된 글이 없습니다 | 새 글이 게시되면 이곳에 표시됩니다 | 없음 |
| 카테고리 없음 | 카테고리 없음 | 홈의 전체 최신 글은 정상 표시 | 섹션 자체 숨김 |
| 빈 카테고리/태그 | 이 주제에는 글이 없습니다 | 다른 주제를 둘러볼 수 있음 | 홈으로 |
| 404 | 페이지를 찾을 수 없습니다 | 주소가 바뀌었거나 글이 없음 | 홈으로, 최신 글 3개 |
| 외부 이미지 실패 | 이미지 자리 유지 | 대체 텍스트와 실패 문구 | 원본 링크가 안전할 때만 열기 |

404와 빈 상태에서도 header/footer를 유지해 막다른 화면을 만들지 않는다. 빌드된 정적 사이트는 런타임 데이터 fetch에 의존하지 않으므로 일반적인 네트워크 오류 화면은 만들지 않는다.

### 프리뷰·게시 앱

오류 문구는 “무엇이 실패했는지 + 콘텐츠가 게시되었는지 + 다음 행동” 순서로 쓴다.

| 코드/원인 | 사용자 메시지 | 복구 |
|---|---|---|
| Notion 403 | Notion 페이지 접근 권한이 없습니다. 아직 게시하지 않았습니다. | 연결/공유 확인 |
| Notion 429 | Notion 요청이 많아 잠시 불러오지 못했습니다. | 안내 시각 이후 재시도 |
| timeout | 응답이 늦어 프리뷰를 만들지 못했습니다. | 재시도 |
| unsupported block | 일부 블록은 표시되지 않을 수 있습니다. | 경고로 위치 안내, 게시 허용 정책에 따름 |
| unsafe image | 안전하지 않은 이미지 주소가 있어 변환을 중단했습니다. | Notion에서 HTTPS 이미지로 교체 |
| GitHub 권한 | 대상 저장소에 쓸 수 없습니다. 아직 게시하지 않았습니다. | GitHub 재동의/저장소 확인 |
| Actions 실패 | 글은 commit되었지만 배포가 실패했습니다. | Actions 로그 열기 |
| offline | 인터넷 연결이 없어 최신 내용을 확인할 수 없습니다. | 연결 후 재시도 |

민감한 provider 응답, token, cookie, repository 내부 오류 원문은 사용자 메시지나 로그에 노출하지 않는다.

## 14. 사용자 여정

### 14.1 작성자: 점검 후 게시

```text
Notion 작성
  → 앱에서 page 발견·구조 판별
  → 칸반 표시
  → 카드의 미리보기 열기
  → 서버가 최신 권한·원문 조회
  → 글 상세/홈 및 모바일 폭 점검
  → 경고가 있으면 Notion에서 수정 후 다시 프리뷰
  → 프리뷰 닫기
  → 카드를 게시 중 column으로 이동
  → 서버가 최신 원문·GitHub 권한 재검증 후 commit
  → Actions/Pages 상태 확인
  → 게시 완료 카드에서 실제 글 열기
```

프리뷰를 건너뛰고 바로 게시하는 경로도 유지한다. 프리뷰 완료 여부를 저장하거나 게시 조건으로 쓰지 않는다.

### 14.2 작성자: 게시 실패 복구

```text
게시 중
  → 오류 원인 범주 표시
  → 화면 상태가 보관 중으로 복귀
  → 권한/Notion 콘텐츠/Actions 로그 중 해당 복구 행동 수행
  → 필요하면 프리뷰 재확인
  → 다시 게시 중으로 이동
```

commit 이후 응답 유실 또는 재시도는 중복 commit을 만들 수 있음을 기술 세부 정보 영역에서 알리되, 일반 오류 메시지의 주 문장으로 사용하지 않는다.

### 14.3 독자: 주제로 글 발견

```text
홈 방문
  → 소개로 블로그 성격 파악
  → 카테고리 선택
  → 제목·설명·날짜로 글 비교
  → 글 상세
  → 태그 또는 이전/다음 글로 이어 읽기
```

### 14.4 독자: 직접 링크로 유입

```text
검색/공유 링크로 글 상세 진입
  → 제목·설명·날짜·카테고리로 맥락 파악
  → 목차로 원하는 절 이동
  → breadcrumb/사이트명으로 홈 이동
  → 관련 분류 탐색
```

## 15. 범위 분리

### 15.1 경험 MVP

기존 제품 경계를 유지하며 다음 블로그 경험 릴리스에 포함한다.

- 공통 header/main/footer, skip link, 반응형 shell
- 홈 최신 글 12개, 선택적 카테고리 요약, 강화된 첫 게시 전 빈 상태
- `/posts/` 전체 글 목록
- 카테고리 0–1개와 태그 0–5개의 Notion 명시 속성 정규화
- 카테고리 정적 목록 route. 태그는 카드·글 상세에 표시하되 태그별 route는 후속 범위
- 글 카드, breadcrumb, 설명·게시일·수정일, 태그
- h2 3개 이상일 때 목차, 본문 typography, 이미지 실패·코드 overflow 처리
- 404와 빈 분류 상태
- 게시 전 글 상세/홈 프리뷰와 3개 viewport 전환
- 프리뷰 loading, 권한, rate limit, timeout, 변환 오류 상태
- WCAG 2.2 AA 기준과 reduced motion
- user/project base path 회귀 검증, JavaScript 없는 핵심 탐색

경험 MVP를 구현하려면 최소한 다음 계약 변경을 제품 명세에 먼저 반영해야 한다.

- `PublishDocument`와 content collection에 optional `category`, `tags` 추가
- 서버의 Notion 속성 정규화와 안전한 분류 slug 생성
- 프리뷰 요청/응답의 소유권·비영속·민감정보 제외 계약
- template version 상승과 기존 게시 저장소 파일 갱신 정책

사이트명과 소개는 설정 저장 계약이 아직 없으므로 경험 MVP에서는 안전한 기본값(`Notion Blog`, 기본 소개)을 쓴다. 사용자 맞춤 설정은 아래 후속 범위로 둔다.

### 15.2 후속 범위

- 사용자별 사이트명, 소개, 프로필 이미지, 소셜 링크 설정
- 글이 많아질 때 `/posts/` 정적 페이지네이션
- 정적 검색 index와 클라이언트 검색(외부 서비스·DB 없음)
- dark theme와 시스템 설정 연동
- RSS, sitemap, Open Graph 이미지, canonical URL 고도화
- 태그별 목록 route, 태그 전체 목록과 인기 태그
- 관련 글 추천(같은 태그 기반의 결정적 정적 계산)
- 표, 목록, 수식, video/embed 등 Notion block 지원 확대
- 프리뷰 diff, 지원하지 않는 block의 본문 내 위치 강조
- 다국어 locale과 날짜/route 전략
- 테마 프리셋. 사용자 임의 CSS는 보안·지원 비용 검토 전 제외
- 읽기 시간, 공유 버튼, 글 archive(연/월)

DB, 영구 프리뷰 이력, 서버 검색, 댓글, 분석 수집은 요구가 생겼을 때 별도 ADR과 개인정보 검토 후 판단한다.

## 16. 검증과 수용 기준

### 기능

- 글 0개/1개/13개, 분류 없음/한글/중복 정규화, 태그 0개/5개를 fixture로 검증한다.
- 홈, category, tag, post, 404의 정적 build 결과에 올바른 base path가 적용된다.
- 프리뷰와 실제 게시 산출물이 동일한 내부 문서 fixture에서 동일한 콘텐츠 구조를 보인다.
- 프리뷰 이후 Notion이 바뀌면 게시 결과는 최신 원문을 사용한다.
- JavaScript를 끈 공개 블로그에서 모든 글·분류 링크와 details가 동작한다.

### 반응형·시각

- 320, 390, 768, 1024, 1440px에서 홈·분류·상세·404를 screenshot 비교한다.
- 200% 확대에서 중요 콘텐츠와 행동이 겹치거나 잘리지 않는다.
- 긴 한글/영문 제목, 200자 URL, 긴 코드, 세로·가로 이미지로 overflow를 검증한다.
- 외부 이미지 실패와 빈 description에서도 레이아웃이 유지된다.

### 접근성

- 키보드만으로 skip link, header, 목록, breadcrumb, 목차, details, 이전/다음 글을 순서대로 사용할 수 있다.
- axe 자동 검사에 serious/critical 위반이 없다.
- VoiceOver로 화면 제목, 현재 내비게이션, 날짜, 분류, 프리뷰 상태와 오류를 이해할 수 있다.
- 모든 상태 조합이 색상 없이도 텍스트로 구분된다.
- reduced motion에서 불필요한 애니메이션이 없다.

### 성능

- 공개 사이트 핵심 화면은 런타임 API 요청 없이 정적으로 제공한다.
- font는 system stack을 우선해 렌더 차단 요청을 만들지 않는다.
- 목록 이미지를 후속 도입할 때 크기 속성, lazy loading, 적절한 responsive source를 요구한다.
- template 추가 JavaScript는 목차 등 네이티브 HTML로 해결할 수 없는 기능에만 허용한다.

## 17. 의사결정이 필요한 항목

구현 착수 전에 다음을 제품 명세에서 확정한다.

1. 고정한 Notion 속성명 `Blog Category`/`Blog Tags`의 사용자별 mapping을 후속에 허용할지
2. 프리뷰를 modal로 둘지 route 기반 전체 화면으로 둘지. 모바일·deep link 불필요 조건에서는 route 기반 dialog가 권장된다.
3. 기존에 게시된 저장소를 다음 게시 때 template version 기준으로 전면 갱신할지, migration을 별도로 실행할지
4. 분류 slug의 Unicode 허용 여부와 hash suffix 길이
5. 지원하지 않는 Notion block을 경고 후 생략할지, 변환 전체 실패로 처리할지

기본 권고는 속성명 고정, 비영속 route 기반 프리뷰, 다음 게시 시 결정적 template 갱신, ASCII slug + 안정적 hash, 정보 손실 가능 block은 명시적 경고 또는 실패다.
